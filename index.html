1. Justificación de las Plataformas y Herramientas de Versionamiento

Para el desarrollo del proyecto web se seleccionó un ecosistema de herramientas distribuido, robusto y altamente compatible con estándares de la industria tecnológica. A continuación se justifica técnicamente cada elemento:

Git (Sistema de Control de Versiones)

Motor Local Distribuido (DVCS)

Git fue seleccionado por ser un sistema de control de versiones distribuido que opera a través de instantáneas inmutables (*snapshots*). Cada confirmación (*commit*) se indexa mediante sumas de verificación criptográficas SHA-1/SHA-256, garantizando la integridad absoluta del historial frente a corrupciones de datos.

  • Operación Offline y Alta Velocidad: Las operaciones de consulta, commit y branching se resuelven en milisegundos sin requerir conexión a internet.
  • Ramificación Ultraligera (*Lightweight Branching*): Permite crear, alternar y fusionar ramas de forma instantánea sin penalización de almacenamiento.
  • Trazabilidad y Respaldo Total: Cada desarrollador cuenta con una réplica idéntica y completa del repositorio histórico.

GitHub (Plataforma Remota & DevOps)

Alojamiento en la Nube & Colaboración

GitHub actúa como el nodo remoto centralizado en la nube para la sincronización del equipo, gobernanza del código fuente y automatización de despliegues.

  • Pull Requests y Code Review: Permite revisar cambios por pares antes de incorporar código en ramas críticas como develop o main.
  • Integración Continua (CI/CD): A través de GitHub Actions se ejecutan pipelines automatizados de construcción, validación y entrega.
  • Gestión de Incidentes: Vinculación directa entre commits, ramas, issues y tableros de avance del proyecto.

Laragon (Entorno de Desarrollo Local)

Pila WAMP / Apache / PHP 8.3

Se seleccionó Laragon sobre alternativas convencionales debido a su diseño moderno, rapidez de arranque y aislamiento total en Windows:

  • Bajo consumo y portabilidad: Arquitectura optimizada que no sobrecarga el sistema operativo ni ensucia el registro.
  • Soporte PHP 8.3 & Virtual Hosts: Permite probar la aplicación en un servidor Apache nativo idéntico al entorno de producción con redirección automática de dominios locales (ej. proyecto.test).
  • Integración nativa con Git: Terminal integrada con soporte inmediato para comandos de Git y Node.js.

Cloud Host (Plataforma de Despliegue en la Nube)

Hosting Continuo / Alta Disponibilidad

La publicación del proyecto en un Cloud Host (Render / GitHub Pages / Railway / Vercel) garantiza la disponibilidad pública y permanente de la solución:

  • Disponibilidad 24/7 y SLA Elevado: La infraestructura en la nube elimina la dependencia de equipos físicos locales.
  • Certificados SSL/TLS Automáticos: Tráfico cifrado mediante HTTPS sin costo adicional de gestión.
  • Continuous Deployment (CD): Cada git push a la rama main activa un webhook que recompila y despliega el sitio automáticamente.

2. Flujo de Trabajo del Control de Versiones

Se implementó un modelo de ramas robusto basado en **Gitflow**, adaptado rigurosamente al ciclo de vida del proyecto mostrado en el caso práctico. Este flujo garantiza la estabilidad del código en producción y promueve el desarrollo modular.

Estructura y Jerarquía de Ramas

main Producción / Live

Contiene el código 100% estable y verificado. Es la rama enlazada directamente con el Cloud Host para despliegue continuo. Cada versión se marca con etiquetas semánticas (tags).

develop Integración

Rama central de desarrollo. En ella se integran todas las características terminadas antes de pasar a producción mediante fusiones estructuradas sin avance rápido (--no-ff).

feature/* Fases y Módulos

Ramas efímeras creadas a partir de develop para cada fase del caso práctico:
• feature/analisis-problema
• feature/generacion-ideas
• feature/diseno-planificacion
• feature/implementacion-web

hotfix/* Mantenimiento Crítico

Ramas de emergencia bifurcadas desde main para corregir errores críticos en producción. Una vez solucionado, se fusionan tanto a main como a develop.

Políticas de Versionamiento Semántico y Commits
Convención de Mensajes (Conventional Commits):
  • feat: Incorporación de una nueva funcionalidad.
  • fix: Corrección de un fallo o bug.
  • docs: Actualización de documentación o README.
  • style: Ajustes visuales de formato sin impacto lógico.
  • refactor: Optimización y reestructuración de código.
Versionado Semántico (SemVer) & Tags:

Se utiliza el formato estándar vMAJOR.MINOR.PATCH. Para esta entrega se etiqueta formalmente:

tag: v1.0.0 (Caso Práctico Finalizado)

3. Parámetros de Configuración de las Plataformas y Herramientas

A continuación se presentan los parámetros exactos y comandos de configuración establecidos en el entorno local (Git CLI) y en la plataforma remota (GitHub):

PowerShell / Git Bash - Configuración del Alumno
# 1. Configuración de Identidad Global del Alumno
$ git config --global user.name "Julio Guzman"
$ git config --global user.email "23040086@alumno.utc.edu.mx"

# 2. Configuración de Saltos de Línea Windows CRLF a Linux LF
$ git config --global core.autocrlf true

# 3. Rama Principal Predeterminada
$ git config --global init.defaultBranch main

# 4. Gestor de Credenciales Seguro de Windows
$ git config --global credential.helper manager

# 5. Estrategia de Pull (Fast-Forward Seguro)
$ git config --global pull.rebase false

# 6. Vinculación del Repositorio Remoto en GitHub
$ git remote add origin "https://github.com/AlejandroDeveloperJunior/GuzmanJuarezJulioFranciscoAlejandro_DWI_U2.git"

# 7. Verificación de Parámetros Activos
$ git config --list --show-origin
Descripción Técnica de Parámetros
user.name & user.email:

Establecen la autoría criptográfica en cada objeto commit para auditoría y trazabilidad en GitHub.

core.autocrlf = true:

Normaliza los saltos de línea convirtiendo CRLF de Windows a LF en el repositorio y viceversa al clonar, evitando inconsistencias entre sistemas operativos.

credential.helper = manager:

Almacena tokens de GitHub en el Administrador de Credenciales de Windows con cifrado seguro.

Archivo .gitignore:

Previene la filtración de secretos (.env), dependencias pesadas (/vendor) y temporales del servidor.
